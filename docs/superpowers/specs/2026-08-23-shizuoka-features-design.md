# 静岡大会仕様 拡張設計

作成日: 2026-08-23
対象: blockly-chaser-shizuoka (一関版 v4.5.0 フォーク)
大会: U-16プログラミングコンテスト静岡大会 (2026年10月)

## 背景

参加者は練習環境 [chaser.u15-ichinoseki.org](https://chaser.u15-ichinoseki.org/)（一関版 v4.5.0）で
プログラムを作成し、`.blch` ファイルを持ち込む。本サーバーはその配信ファイルと同一の内容から
分岐しているため、`.blch` はそのまま読み込める。

大会運営のために以下の3機能を追加する。

- **A. マップの静岡大会仕様化**
- **C. 試合動画の閲覧機能**
- **B. トーナメント画面**

3機能は互いに独立している。A → C → B の順に実装する。

## 全体方針

### 既存資産を壊さない

`chaser/server.js` は 1700 行超の状態機械で、試合進行の中核である。ここへの変更は
**試合終了時のフック1本のみ**に限定する。新機能はすべて独立したモジュール
（`tournament/`, `movies/`）とルートに閉じ込める。

### room_id は絶対に変更しない

参加者の `.blch` に含まれる `server_join` ブロックは `room_id`（`room_001` 〜 `room_114`）を
フィールド値として保持している。**room_id を変更すると参加者のプログラムのマップ選択が失われる。**

したがってマップの静岡仕様化では `name` と `map_data` のみを変更し、`room_id` は現行のまま維持する。

### 権限モデル

既存コードに認証機構は存在しない。運営操作用に環境変数 `ADMIN_KEY` による最小限の認証を導入する。

- `ADMIN_KEY` 未設定時、管理ページは **localhost からのみ** アクセス可能
- `ADMIN_KEY` 設定時、Cookie に保存されたキーが一致する場合のみアクセス可能
- 参加者向けページ（閲覧・トーナメント表示）は認証不要

これは大会運営用の運用上の仕切りであり、暗号学的な保護ではない。会場LAN内での運用を前提とする。

## A. マップの静岡大会仕様化

### 現状

`load_data/game_server_data/` に 28 個の JSON がある。

| room_id | 用途 | 現在の名前 |
|---|---|---|
| `room_001`〜`room_009` | CPU対戦・汎用 | ランダム / 対称 / ブロック / シンプル / 迷路 など |
| `room_010`〜`room_014` | CPU対戦・大会 | 一関23 / 一関24予選 / 初戦 / 準決 / 決勝 |
| `room_101`〜`room_109` | 対人・汎用 | 同上 |
| `room_110`〜`room_114` | 対人・大会 | 同上 |

マップ JSON の構造:

```json
{
  "name": "一関24決勝マップ",
  "room_id": "room_014",
  "map_size_x": 15,
  "map_size_y": 17,
  "map_data": [[0, 2, 0, ...], ...],
  "cool": { "status": false, "turn": false, "x": 4, "y": 8 },
  "hot":  { "status": false, "turn": false, "x": 10, "y": 8 },
  "cpu":  { "level": 2, "turn": "hot" },
  "turn": 200
}
```

`map_data` の値: `0` = 床、`1` = アイテム、`2` = ブロック。

### 変更内容

汎用マップ（`room_001`〜`009` / `room_101`〜`109`）は大会に依存しないため **名前も内容も変更しない**。
参加者が練習で慣れた挙動をそのまま維持する。

大会マップ（`room_010`〜`014` / `room_110`〜`114`）を静岡大会仕様に差し替える。

| room_id | 新しい名前 | ターン数 | 性格 |
|---|---|---|---|
| `room_010` / `room_110` | 静岡練習マップ | 100 | 練習用・素直な構成 |
| `room_011` / `room_111` | 静岡予選マップ | 150 | アイテム多め・探索重視 |
| `room_012` / `room_112` | 静岡初戦マップ | 150 | 通路が分かれる中庸な構成 |
| `room_013` / `room_113` | 静岡準決マップ | 150 | ブロック多め・閉じ込め狙いが成立 |
| `room_014` / `room_114` | 静岡決勝マップ | 200 | 最も複雑・長期戦 |

CPU対戦版（`0xx`）と対人版（`1xx`）は同一の `map_data` を持ち、`cpu` フィールドの有無だけが異なる
（現行の一関版と同じ関係）。

### マップ生成

手書きは誤りが混入しやすいため、生成スクリプト `tool/generate_maps.js` を作る。

- 点対称なマップを生成する（`cool` と `hot` の初期位置が盤面中心に対して対称）
- 生成パラメータ（サイズ・ブロック数・アイテム数・ターン数・乱数シード）を指定する
- **乱数シードを固定**し、同じ入力から常に同じマップが再現できるようにする

### 検証

`tool/validate_maps.js` と、それを呼ぶテストを作る。全マップに対して以下を検査する。

1. `map_size_x` × `map_size_y` と `map_data` の実寸が一致する
2. `map_data` の値がすべて `0` / `1` / `2` のいずれか
3. `cool` と `hot` の初期位置が盤面内で、かつ床（`0`）である
4. `cool` と `hot` が互いに到達可能（幅優先探索。ブロックで分断されていない）
5. `room_id` がファイル名と対応し、28個すべてが存在する
6. `turn` が正の整数

検査 4 が最も重要である。分断されたマップでは相手に接触できず、必ずスコア勝負になってしまう。

## C. 試合動画の閲覧機能

### 目的

運営が用意した試合動画（過去大会の記録、模範対戦、当日のリプレイなど）を参加者が閲覧できるようにする。

### 保存方式

`load_data/movie_data/` に動画ファイルを置き、同ディレクトリの `movies.json` にメタデータを持つ。

```json
{
  "movies": [
    {
      "id": "final-2025",
      "file": "final-2025.mp4",
      "title": "2025年 決勝戦",
      "description": "アイテム収集型とアタック型の対戦",
      "date": "2025-10-12",
      "order": 1
    }
  ]
}
```

`movies.json` に載っていないファイルがディレクトリにあった場合は、ファイル名から
自動的にエントリを生成して一覧に出す。運営がファイルを置くだけで公開できる。

**メタデータはリクエストごとに読み直す。** 動画を追加してもサーバー再起動は不要。

### 対応形式

ブラウザの `<video>` タグで再生できる形式に限る: `.mp4` / `.webm` / `.m4v`。
それ以外の拡張子は一覧から除外する。

### 配信

`express.static` で `/movies/file` にマウントする。Range リクエストに対応するため
`express.static` の既定動作をそのまま使う（シークが効く）。

### 画面

- `/movies` — 一覧。タイトル・説明・日付を並べる
- `/movies/:id` — 再生ページ。`<video controls>` と説明

デザインは既存の `menu.css` / `style.css` のトーンに合わせる。

### 運営によるアップロード

`/movies/admin`（要 `ADMIN_KEY`）で以下を行う。

- 動画ファイルのアップロード（`multipart/form-data`）
- タイトル・説明・並び順の編集
- 動画の削除（`movies.json` からの除外。ファイル自体は残す）

アップロードには `multer` を使う。上限は 1 ファイル 500MB、拡張子は上記3種のみ許可する。
ファイル名はサーバー側で安全な文字列に正規化する（パストラバーサル対策）。

## B. トーナメント画面

### 目的

対戦表を参加者・観客に見せる。運営が勝敗を記録し、勝者を次の回戦に進める。

### 方針

**手動入力を正とする。** 試合結果の自動記録は「候補」を提示するだけで、
盤面へ反映するかどうかは必ず運営が判断する。自動反映は事故が起きたときに取り返しがつかない。

### データモデル

`load_data/tournament/tournament.json` に保持する。

```json
{
  "title": "U-16プログラミングコンテスト静岡大会 2026",
  "players": [
    { "id": "p1", "name": "しずおか一号", "school": "○○中学校" }
  ],
  "rounds": [
    {
      "name": "1回戦",
      "matches": [
        {
          "id": "r1m1",
          "coolId": "p1",
          "hotId": "p2",
          "winnerId": "p1",
          "coolScore": 12,
          "hotScore": 8,
          "note": "アタックにより",
          "roomId": "room_111",
          "movieId": "final-2025"
        }
      ]
    }
  ]
}
```

- `players` は参加者名簿。`id` は内部識別子
- `rounds` は回戦の配列。`matches` はその回戦の対戦カード
- `coolId` / `hotId` が `null` の場合は「勝者待ち」として表示する
- `movieId` を設定すると、その試合から動画ページへリンクする（C機能との接続点）

### 勝者の繰り上がり

回戦 N の試合 i の勝者は、回戦 N+1 の試合 `floor(i/2)` の
`coolId`（i が偶数）または `hotId`（i が奇数）に入る。

この計算は運営が「勝者を確定」を押したときにサーバー側で行う。
入力ミスに備え、確定後も手動で上書きできる。

### 画面

**`/tournament`（参加者・観客向け、認証不要）**

対戦表を CSS Grid で描画する。回戦を列、試合を行として並べ、勝者を強調する。
外部ライブラリは使わない（このプロジェクトは CDN を使っておらず、会場LANでは
外部への到達性が保証されないため）。

30秒ごとに `/api/tournament` をポーリングして自動更新する。
Socket.IO を使わないのは、トーナメント表の更新頻度が低く、
`chaser/server.js` の Socket.IO 名前空間に手を入れたくないため。

**`/tournament/admin`（運営向け、要 `ADMIN_KEY`）**

- 参加者の登録・編集
- 回戦と対戦カードの作成
- 勝敗・スコアの入力、勝者の繰り上がり実行
- 自動記録された試合結果の一覧から、対戦カードへ結果を取り込む

### 試合結果の自動記録

`chaser/server.js` の試合終了は 2 箇所。

| 行 | 関数 | 状況 |
|---|---|---|
| 265 | `game_time_out()` | 制限時間切れ |
| 421 | `game_result_check()` | 通常の勝敗確定 |

どちらも `io.in(room).emit("game_result", ...)` を呼ぶ直前に、
`server_store[room]` から以下が読める。

- `cool.name` / `hot.name` — プレイヤー名
- `cool.score` / `hot.score` — スコア

新規モジュール `tournament/result_log.js` に `recordResult()` を作り、
上記2箇所から呼ぶ。`chaser/server.js` への変更は **require 1行と呼び出し2行のみ**。

記録内容:

```json
{
  "recordedAt": "2026-10-12T04:23:11.000Z",
  "roomId": "room_111",
  "coolName": "しずおか一号",
  "hotName": "しずおか二号",
  "coolScore": 12,
  "hotScore": 8,
  "winner": "cool",
  "info": "アタックにより"
}
```

直近 200 件をメモリに保持し、`load_data/tournament/results.jsonl` に追記する。
ファイルへの追記は非同期で行い、**失敗しても試合進行を妨げない**
（`recordResult()` 内で例外を握りつぶし、ログに残すだけにする）。

### 永続化とクラッシュ耐性

`tournament.json` は変更のたびにファイルへ書き出す。
書き込みは一時ファイルへ書いてから `rename` する（アトミック置換）。
大会中にサーバーが落ちても、対戦表は最後に保存された状態から復帰できる。

## 実装順序

1. **A-1** マップ生成・検証スクリプトとテスト
2. **A-2** 静岡大会マップの生成と差し替え
3. **C-1** 動画の一覧・再生（閲覧側）
4. **C-2** 動画の管理画面（アップロード）
5. **B-1** トーナメントのデータモデルと永続化
6. **B-2** トーナメント表示画面
7. **B-3** トーナメント管理画面
8. **B-4** 試合結果の自動記録フック

各段階でテストを書き、コミットする。

## テスト方針

`node --test` を使う（追加依存なし）。`package.json` に `"test": "node --test"` を追加する。

| 対象 | テスト内容 |
|---|---|
| マップ検証 | 28マップすべてが検証6項目を通る |
| マップ生成 | 同じシードから同じマップが出る |
| 動画メタデータ | `movies.json` 不在・壊れた JSON・未登録ファイルの扱い |
| ファイル名正規化 | `../` を含む名前が無害化される |
| トーナメント進行 | 勝者が正しいスロットへ繰り上がる |
| トーナメント永続化 | 保存 → 読み込みで内容が一致する |
| 結果記録 | 書き込み失敗時に例外が呼び出し元へ漏れない |
| 権限 | `ADMIN_KEY` 不一致で管理APIが 403 を返す |

HTTPレベルの確認は、テスト内でサーバーを起動して `fetch` で叩く。

## 非目標

以下は今回作らない。

- 参加者自身によるアカウント登録・ログイン
- トーナメント表の自動組み合わせ抽選（運営が手で組む）
- 試合の自動録画（動画は運営が別途用意して置く）
- スイス式・総当たりなどトーナメント以外の方式
